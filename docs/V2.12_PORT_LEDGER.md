v2.1.5, 2026-11-11); the previous port (`docs/V2.3_PORT_LEDGER.md`) stopped at

## Why this port was urgent

The engine archives live in upstream's public bucket (`PUB_BASE`), not in this
repo. On 2026-11-10 the bucket started serving the Chromium 157.0.8103.50 build
(etag `57a2ea08…-26` for Windows) while the fork's `runtime.json` still named
156.0.8078.48. A fresh install or a forced reinstall therefore extracted a 157
engine under profiles migrated to 156, and the stored etag never matched the
manifest again. Pointing `runtime.json` at the build the bucket serves fixes it.

### Upstream issue #154: extension welcome page on every launch

Not reproduced on 2026-11-18, nor on 2026-11-19 with upstream 2.1.4's own
flags, so nothing was changed. The report is against upstream launcher 2.1.4:
AdBlock or Tampermonkey reopen their welcome page each time a profile starts.

Setup:

- The real engine (`ShardX-Windows` 157.0.8103.50), headless, on throwaway
  user-data directories.
- The flags `launch.rs` passes:
  - `--load-extension` and `--disable-extensions-except` on stable directories;
  - `--restore-last-session`, `--hide-crash-restore-bubble` and `--no-first-run`;
  - `--fingerprint-profile` holding an empty object.
- On 2026-11-19, also the flags upstream 2.1.4 passes to an engine that loads
  extensions past the Safe Browsing gates (this engine does):
  `--load-extension` alone plus `--shardx-extension-library` on the library
  folder, and no `--restore-last-session`.
- Tampermonkey 5.5.1 and AdBlock 6.54.0 (unpacked from their Web Store CRX
  files).
- A probe extension that opens a time-stamped page from `runtime.onInstalled`.

Before each relaunch the opened pages were closed, as in the report.

| Run | Launch 1 | Launch 2 | Launch 3 |
|---|---|---|---|
| All three, browser closed cleanly | 3 welcome pages | none | none |
| Probe only, closed cleanly | 1 | none | none |
| Forced stop after launch 1, install not yet finished | none | Tampermonkey's page, once | none |
| Probe, welcome page left open at quit | 1 | the same page, same URL | the same page again |
| 2026-11-19, all three, this fork's flags, closed cleanly | 3 welcome pages | none | none |
| 2026-11-19, all three, upstream 2.1.4's flags, closed cleanly | 3 welcome pages | none | none |

An extension is installed once per profile and kept. The library keeps each
one in `extensions/<id>`, so the unpacked extension's ID never changes. A
welcome page left open at quit comes back through session restore. That looks
like the report. It came back with the same URL even when the extension itself
was not loaded, so it was not a new install.

Not covered:

- the upstream 2.1.4 launcher itself (only its flags were);
- a visible window;
- a full fingerprint profile.

### Checksums behind #321

The four new archives were downloaded from the bucket and checked against the
entity tag upstream's manifest names: Windows (25 parts), Linux (26) and macOS
(20) match their multipart tags with 8 MiB parts, and the fingerprint archive
matches its MD5 tag. Their SHA-256 are in `runtime.json`. Before this, `main`
carried a SHA-256 for the three Widevine archives only, so the launcher and the
SDKs refused to install the engine, Linux, macOS and fingerprint archives.
