## Findings and evidence

### P1-01 — APPROVE

R1 now defines `v2_bootstrap_guards` with primary key `(server_instance_id, tenant_id)` and states `unused|reserved|consumed|closed|recovery_required`; it explicitly does not infer freshness from an empty approval table (`ADR:743-750`). The confirmation has an immutable instance/tenant/account/device/key tuple, distinct role-separated IDs, pinned encodings/suites, terminal fields, and consumed approval replay ID plus three hashes (`ADR:752-767`). This is the right lifetime scope: it is deliberately not epoch-scoped, so an epoch transition cannot create a second opportunity.

The transition table is sufficiently fail-closed: confirmation is reserved only after fresh-tenant provenance, one active owner, exact pending device and recomputed key IDs; consumption atomically inserts the approval, links exact evidence, closes the guard, activates the device, stores the response and writes audit; cancellation/revocation closes the guard; inconsistencies become `recovery_required` (`ADR:774-783`). There is no offline confirmation expiry, replacement, delete/reinsert, force reset, or implicit reset; the ADR explicitly makes any future replacement policy a separately reviewed decision (`ADR:785-794`). That choice is operationally strict but complete and does not leave security semantics to an implementer.

Epoch and restore behavior is explicit: pending confirmation closes on recognized epoch increase; terminal rows remain historical; missing or contradictory restore evidence yields `recovery_required`, never `unused`, and an empty restored DB is not treated as fresh (`ADR:796-808`). S6 rechecks current active approval, equality fields, validity/revocation, context, tuple and all three hashes, and treats the link as evidence rather than reusable permission (`ADR:810-817`). The plan requires exact active `DeviceApprovalV2` linkage for `FirstRootSelfGrant` (`plan:774, 812-819`), so this closes the prior review's missing linkage without inventing an external transparency ledger. The ADR also provides read-only status after CLI response loss and forbids reissue (`ADR:819-828`).

**Residual boundary, not a blocker:** the plan explicitly does not claim detection of selective same-epoch malicious control-plane rollback (`plan:373-376`; ADR:796-808). R1 correctly preserves that boundary rather than pretending the guard solves it.

### P1-02 — APPROVE

R2 directly addresses the old no-device/device-FK cycle. It records the current runtime gap—v2 login is absent, current `AuthUser` is v1-backed, and `v2_sessions.device_id` is non-null/FK-bound—rather than presenting the proposal as implemented (`ADR:830-838`; `server/src/auth.rs:139-160`, `server/src/routes/mod.rs:18-38`, `server/migrations/0004_v2_team_fleet.sql:93-103`).

The proposed flow is a sound separation of principal classes: login yields only a short-lived, non-refreshable account pre-device ticket stored by hash and limited to enrollment/session-proof endpoints (`ADR:840-850`). Enrollment binds instance, epoch, tenant, account, ticket, challenge, nonce, both public keys, both derived IDs, suites and expiry in a closed map; the challenge is consumed atomically with pending-device creation (`ADR:852-872`). This is materially stronger than treating account ID as device ID.

Most importantly, R2 supplies an actual HPKE private-key possession bridge rather than treating a public-key fingerprint as possession: the server encrypts a random secret to the candidate HPKE key, the client returns the decrypted secret plus an Ed25519 signature over the exact binding and secret, and the server compares the secret hash, verifies the signature and rechecks context/key equality in one transaction (`ADR:874-908`). It consumes the challenge and ticket and inserts the actual device-bound session atomically; pending/setup sessions are explicitly limited and do not themselves authorize operations (`ADR:910-938`). This meets the original review's required distinction between signing proof and HPKE PoP and preserves the plan's separate two-key lifecycle requirement (`plan:368-370`).

**Residual boundary, not a blocker:** R2's session durations and endpoint names are new design choices, but they are specified, bounded and consistently tied to live predicates. They do not claim current runtime support.

### P1-03 — REVISE (remaining blocker)

R3 gets most of the security ordering right. It keeps the plan's exact signed approval container rather than introducing a mutable approval ID (`ADR:940-950`), defines a fixed operation scope and actor-bound unique identity, reserves the approval replay ID globally within instance/tenant/domain, stores exact request/body and signed-container hashes, and rejects changed bytes/actor/path/epoch without mutation (`ADR:951-966`). The exact closed `DeviceApprovalReceiptV2`, exact response bytes/hash, and no reserialization on replay are concrete (`ADR:968-982`). The lookup ordering is also correct in principle: authenticate the current device session and live context first, then parse/hash and look up; exact-hit replay is checked before first-creation emptiness; miss path performs signed-record/equality/live-authority and D1 guards (`ADR:984-1025`).

The remaining defect is architectural rather than a missing hash. The frozen plan defines one common durable idempotency authority, `v2_idempotency`, keyed by `(server_instance_id, tenant_id, actor_device_id, operation_scope, idempotency_key)`, with exact request/response bytes and `retained_until` (`plan:1090`, `1095-1100`). It also requires approval mutation + exact response + structured audit in the same transaction and requires response retention/GC rules for mutation replay (`plan:1106-1107`, `1422-1423`). R3 instead says to create a separate `v2_approval_operations` ledger (`ADR:948`) but never gives its schema, composite foreign keys, retention/GC floor, migration relationship to `v2_idempotency`, or a rule saying whether the separate ledger or `v2_idempotency` is the single replay authority. The ADR's listed schema at `ADR:1055-1091` includes `v2_idempotency` but does not include `v2_approval_operations`; the approval-specific receipt is described only as a proposed table. That creates two plausible idempotency authorities and leaves an implementer to resolve duplicate-key, close/reopen, retention, and reconciliation behavior.

This is not cured by saying the common enum remains unchanged. The operation identity can be represented in the existing generic row without adding a new enum value, or a separate approval ledger can be an explicitly linked extension—but the ADR must choose and specify one authoritative path. The exact response and live-auth ordering can survive either choice; the current text does not define the durable schema/order between them.

**Minimal required change:** choose one of these, then state it normatively and consistently across R3, ADR 7.1/7.3/10.2 and the plan-derived retention rules:

1. **Use `v2_idempotency` as the sole approval replay authority:** define the exact approval operation's `operation_kind` representation without silently violating the frozen closed enum, add the approval request/receipt fields and unique/global replay reservation as explicit schema constraints, and state its `retained_until`/GC floor and migration/recovery behavior; or
2. **Retain a separate approval ledger:** add its exact schema, instance/tenant/actor/scope/replay keys and equality constraints, exact request/response bytes and hashes, same-transaction relationship to the common `v2_idempotency` row (or explicitly state the common row is not used), retention/GC floor, crash/restart reconciliation, and restore/quarantine behavior. It must be impossible for the two ledgers to disagree about whether an approval committed or what exact response is replayed.

Do not implement or call G2 complete on the strength of R3's current prose. The existing runtime is a baseline defect, not a regression: it currently consumes a replay ID without storing exact approval response bytes/approval state (`server/src/routes/v2.rs:168-199`), and this review does not treat it as evidence of implementation.

### P1-04 — APPROVE

R4 identifies the concrete writer defect at `server/src/enrollment.rs:240-241`: both IDs are derived with `signing_key_id`, while the authoritative library defines `signing_key_id` and distinct `hpke_key_id` domains (`shared/src/keys.rs:52-55, 86-95`). The revised ADR makes the correct derivations normative, including the domain-hash construction (`ADR:1027-1037`; `shared/src/canonical.rs:331-343`), and requires validated raw encodings/suites and complete context equality across enrollment, PoP, confirmation, approval, S6, activation, restore and key-release paths (`ADR:1039-1045`).

The forward rule is appropriately conservative: do not edit shipped migration `0004`; inventory under the exclusive lock, recompute IDs, preserve old bytes/hashes/audit, traverse all downstream references and require trusted instance provenance (`ADR:1047-1055`). Pure pending/untrusted wrong-domain rows may be repaired in one audited transaction only after uniqueness checks and fresh PoPs; anything confirmed, signed, active/trusted, ambiguous or contradictory is quarantined with sessions revoked and original signed material preserved (`ADR:1057-1073`). This directly addresses the prior review's requirement to distinguish never-trusted pending setup from signed/trusted history and avoids silently relabeling signed claims.

**Residual boundary, not a blocker:** quarantine may require operator re-enrollment or a new tenant if no valid issuer exists. That is an explicit safe outcome, not an unsafe automatic repair.

## Overall design verdict

**REVISE.** R1, R2 and R4 are sufficiently complete to approve against their original P1 findings. R3 is not yet complete because its new approval-specific response ledger is not integrated into the frozen idempotency schema/retention/recovery model.
